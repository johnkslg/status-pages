The short version.
  • The two biggest bugs, 17 of the 19 exceptions, are already fixed on main (commit c4089b155, Nov 16). Players still hit them because store builds 0.9.0 and 0.9.1 predate the fix. The next store build should clear them.
  • Almost every native crash looks like the OS killing the game for using too much memory. Each crash we could open shows "Low Memory" warnings first. We can't see where the memory goes because the crash symbols were never uploaded.
  • Around a third of the noise comes from our own test builds (Cozy Moto, Cozy Perf Scenario, an emulator), not from players.

What went wrong, grouped by cause

1. Plants changed the list while it was being read fixed on main
8 occurrences, 3 players, Google Play build 0.9.1 (Pixel 9 Pro XL). "Collection was modified" in PlantTicker.Update. A plant growing could switch another plant on or off, and that edited the list the ticker was walking. The game threw every half second while it happened.
Fix: c4089b155 walks a copy of the list and skips plants removed during the tick (Assets/Scripts/Shop/Farming/PlantTicker.cs).
2. Changing graphics quality touched trees and junk that were already gone fixed on main
9 occurrences in 3 issues, up to 6 players. Google Play build 0.9.0 (Galaxy A56, Galaxy S20 FE) plus our Perf Scenario build. When the player applied a quality level, QualityBasedRenderer and QualityBasedBehaviour on Flowers, Trees and Junk_TallGrass still pointed at renderers inside junk that had been swept or tree towers that had been sold. That threw, and the "applying quality" overlay stayed on screen.
Fix: c4089b155 gives each piece its own quality components, so nothing points into an object that can be destroyed.
Risk left: the fix is in the prefabs, not the code. A new prefab wired the same way would bring it back. An edit-mode test that checks every quality component only points inside its own object would catch that (proposed, not built).
3. The OS killed the game for using too much memory likely
16 native crashes: 7 on Android (inside libc), 9 on iOS (inside UnityFramework or the kernel). Each one we opened showed "Low Memory" warnings just before the crash.
  • Android: the ones we opened are from our own "Cozy Moto" test build 0.9.2 on a Moto G Play 2023 (3 GB, PowerVR GE8320). They all land in the same Nov 16 to 17 overnight window, so they look like one test run on that phone.
  • iOS: one was an App Store 0.8.6 player on an iPhone 13 (iOS 27.2), killed in the render loop after two Low Memory warnings. The other eight have the same one-line shape but are unreadable without symbols.
  • Earlier reports point the same way: Pixel 6 Low Memory on Oct 8 and Oct 26.
4. Smaller ones
  • old build URP decal pass crash (RenderingUtils.SetScaleBiasRt), 2 occurrences, App Store 0.7.6 on an iPhone 12. Old version, nothing to do unless it shows up on 0.9.x.
  • internal 1 ANR on an Android emulator: the game used 1.4 GB and didn't answer a pause in time. Not a player device.

What to do next

  • Ship a store build from current main (0.9.5 or later). That carries c4089b155 and should end 17 of the 19 exceptions. Then check that issues e00e5f2c, 889a9430 and 6ca80bf4 stop.
  • Upload crash symbols with every store build: iOS dSYMs, and Android libunity and libil2cpp symbols. Right now 15 of the 16 native crashes can't be read past "libc" or "UnityFramework".
  • Profile memory on a 3 to 4 GB phone (Moto G Play 2023, iPhone 13). Low Memory warnings come before every native crash we opened.
  • Keep test builds out of the player numbers. Cozy Moto, Cozy Perf Scenario and emulator runs share this project. Filter by bundle id (com.cozycastle.cozycastle for players), or point test builds at their own Unity project or environment.
  • Guard the quality fix: add an edit-mode test that fails when a quality component points outside its own object (proposed).
